# 应用更新与发布

从 0.2.2 起，控制台「系统 → 应用更新」会显示本机版本和 GitHub 稳定版 Release。自动检查默认开启，控制台启动后约 20 秒检查一次，此后每 6 小时检查；可以关闭，也可以点「检查更新」。检查失败不会中断消息收发，不会自动下载安装。

GitHub 源码提交和正式发行版是两件事。客户端只读取 `miku05231/DSH-Fatwhale-QQ` 的稳定版 Release，不跟随 `main` 的每次提交，也不安装草稿、预发布版或旧版本。

## 用户升级

Windows 便携版在发现新版后，可以选择「安装并重启」。确认后才下载安装包，校验 `SHA256SUMS.txt`，检查压缩包路径和版本，备份待覆盖的程序文件，再替换并重启应用。桥接与托盘会暂时退出；NapCat 与 DSH 不会被更新器停止。

更新保留 `config.json`、`state/`、`logs/`、`napcat/`、`qq-workspace/`、人格、记忆、表情包、自定义模型补丁及其它未随发行包提供的文件。用户把数据放到程序文件位置时，安装器拒绝覆盖并提示手动处理。更新不删除未出现在新包中的本机文件。

安装失败会尝试还原已覆盖文件。安装记录、下载包及备份在 `state/updates/`；空间不足、文件被占用或断电后，应先查看该目录的结果和备份，再重试。不要在更新期间手动移动程序目录。

从 0.2.6 起，Windows 的独立 Git 源码目录也可点击「安装并重启」。更新器从官方仓库拉取对应稳定版标签，核对版本与提交，只允许当前分支快进，禁用安装时的 Git hooks。源码有未提交修改、分支已分叉或存在其它 Git 操作时会停止更新，按钮保留显示并说明原因。安装前记录原提交，失败时尝试恢复；本机未跟踪数据不会被覆盖。

以下环境只检查版本，并提供发行页入口：Git worktree、Docker、非 Windows、外部 `QQ_CONFIG` 配置或自定义状态目录。源码用户仍可先保留本机修改，再自行更新；Docker 用户按部署方式更新镜像或重新构建。旧版源码安装需先手动更新一次，才能使用新增的源码更新方式。

没有更新器的旧版需要先手动安装一次 0.2.2 或更新版本。仅下载一个新的启动器 EXE 不能补齐更新功能，应使用完整便携包。

桌面连伴插件随便携包放在 `src/companion/`，沿用旧版更新器已有的程序目录白名单；0.2.3 可直接升级，无需提前替换本机安装器。如果曾从开发版安装过指向顶级 `companion/` 的插件，升级后重新运行 `node tools/install-companion.mjs` 更新已有标记块。更新器不会删除旧目录或改写 DSH profile。

## 作者发布

1. 更新根目录 `package.json` 中的版本，例如从 `0.2.5` 改为 `0.2.6`，提交代码与说明。
2. 检查通过后推送代码，再创建并推送同版本标签：

```powershell
git pull --no-rebase origin main
git push origin HEAD:main
git tag -a v0.2.6 -m "QQ-DSH 0.2.6"
git push origin v0.2.6
```

`.github/workflows/release.yml` 先在 Linux 上验证 DSH Web、无工具聊天与表情概率，再在 Windows 上运行测试运行器、托盘、更新、安装回滚、封装、EXE、连伴、表情概率及管理员权限测试。核对标签与 `package.json` 后，构建完整便携包并隔离安装该实际产物，全部通过才发布 Release。内核测试固定使用 `@deepseek-ai/dsh@0.2.0-rc.2` 与本地假模型，不连接真实 QQ 或在线模型。此流程未运行 Docker 构建或容器测试，Linux 内核检查不代表 Docker 验证：

| 文件 | 用途 |
| --- | --- |
| `qq-bridge-0.2.6-portable-win64.zip` | 客户端自动更新所需的完整 Windows 便携包 |
| `qq-bridge-0.2.6-source.zip` | 源码包 |
| `qq-bridge-launcher-0.2.6.exe` | 单独启动器 |
| `SHA256SUMS.txt` | 三个文件的 SHA-256 |

也可以在 GitHub Actions 的「Windows Release」中手动运行，输入已存在的同版本标签。工作流使用仓库自带的 `GITHUB_TOKEN`，不需要把个人令牌写入工程。需要开启 Actions，并允许该工作流写入仓库内容。已有 Release 不会被覆盖；正式版本有错误时应发布更高版本。

对应版本的说明放在 `docs/releases/v<版本>.md`。工作流发布完成后，运行 `gh release edit v0.2.6 --notes-file docs/releases/v0.2.6.md` 更新说明。

也可在本机运行 `powershell -ExecutionPolicy Bypass -File scripts/make-release.ps1`，把 `dist/release/` 的四个文件一起上传到对应稳定版 Release。单纯提交源码、上传 EXE 或编辑 README 不会触发客户端升级。

客户端下次检查会提示新版。更新提醒依赖客户端访问 GitHub，不是即时消息推送；用户关闭自动检查或应用未运行时，需要下次启动或手动检查。

## 隔离验证

```powershell
node tests/run-all.mjs --only 更新
node tests/run-all.mjs --only exe
node tests/run-all.mjs --only 封装应用
node tests/run-all.mjs --only 公开导出
```

本机生成发行包后，还可以验证实际便携包：

```powershell
powershell -ExecutionPolicy Bypass -File scripts/make-release.ps1
node tests/release-update-test.mjs
```

更新测试使用假 Release、临时目录与假进程，不安装真实在线版本，也不停止本机 QQ、NapCat 或 DSH。界面测试使用 Microsoft Edge 和 Node.js 22+，运行截图和报告留在 `state/`。

实际便携包验证会分别运行固定的 0.2.3 安装器与当前安装器，确认完整新包可安装、`src/companion/` 文件齐全，并保留配置、表情、记忆、工作区以及本机自建的顶级 `companion/` 数据。
