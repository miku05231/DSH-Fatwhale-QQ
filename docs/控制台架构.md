# 控制台架构与功能扩展方法

> 版本：2026-10-20 · 对应代码：`src/webui/`、`src/plugins/`、`launcher/Launcher.ps1`
> 参考项目：[AstrBot](https://github.com/AstrBotDevs/AstrBot)（文档站 <https://docs.astrbot.app/>）

这份文档回答两个问题：

1. 控制台现在**长什么样、每一块归谁管**；
2. 想加功能时**从哪儿加**，为什么这样加（而不是继续往 `src/index.js` 里堆 if）。

---

## 一、参考 AstrBot 的哪些设计

AstrBot 是一个多平台聊天机器人框架，它的 WebUI 与插件体系有几处值得抄：

| AstrBot 的做法 | 我们采用的部分 | 不采用的原因 |
| --- | --- | --- |
| **插件 = 元数据文件 + 事件钩子 + 配置 schema + 可选「插件页」** | 全部采用：`meta` / `onMessage`·`beforeReply`·`afterReply` / `configSchema` / 控制台自动渲染的插件卡片 | 「插件页」需要允许插件注入前端资源，当前是单机自用，等有真实需求再做 |
| WebUI 按域分区（平台、供应商、MCP、技能、插件、知识库、对话管理…） | 采用：概览 / 记忆 / 人格 / 会话 / 模型 / 插件 / 系统 | 没有「平台」「知识库」两个域：本机只有一个 QQ 账号、记忆直接落 Obsidian |
| 插件在 WebUI 里**热重载**（不用重启进程） | 部分采用：控制台能重新扫描目录并改写开关/配置，但**要让桥接真正生效需要重启桥接**，控制台会如实提示 | 桥接是零依赖常驻进程，为了热重载引入 IPC/事件总线不划算；重启桥接在控制台里一键完成（`POST /api/service/bridge/restart`） |
| 插件市场 / 一键安装 | 不采用 | 自用项目，插件就是我们自己写的几个文件 |
| 配置统一 YAML + 页面自动生成表单 | 采用「schema 驱动表单」的思想，但配置直接落 `config.json` 的 `plugins.<name>` | 少一个解析器、少一种格式 |

一句话：**AstrBot 的插件模型（元数据 + 钩子 + schema 表单）和控制台分区方式照抄，运行时复杂度砍到单进程能扛的程度。**

## 二、控制台结构

### 2.1 进程与入口

```
托盘（Launcher.ps1）—— 只负责常驻与退出
 ├─ 左键单击 ──────────────► 打开控制台（Edge --app）
 ├─ 开机自启 ──────────────► bootstrap.ps1（NapCat → 桥接 → 控制台 → DSH → 托盘）
 └─ 右键菜单 ──────────────► 只有「退出（停止桥接与 NapCat）」，DSH 不受影响
控制台（src/webui/server.mjs，默认 127.0.0.1:5830，只绑本机）
 ├─ 静态页：src/webui/public/{index.html, app.css, app.js}
 └─ HTTP API：/api/*
桥接（src/index.js）── WebSocket ──► NapCat（OneBot 11）──► QQ
```

- 控制台**不直接持有**桥接状态，全部走磁盘（`state/*.json`）或服务控制脚本，所以它可以随时重启而不影响桥接。
- 所有 API 只绑 `127.0.0.1`；返回前统一过 `redactSecrets`，密钥不会进前端。

### 2.2 八个页签

| 页签 | 职责 | 主要接口 |
| --- | --- | --- |
| 概览 | 进程状态、连接情况、当前模型、最近忽略原因、快捷服务开关 | `GET /api/overview`、`POST /api/service/<name>/<action>` |
| 记忆 | Obsidian 记忆库统计、检索、笔记读写、打开文件夹 / 用 Obsidian 打开；**记忆反思卡**（立即反思 + 每天定时 + 打开本周那一篇） | `/api/memory/stats`、`/api/memory/search`、`/api/memory/note`、`GET|POST /api/reflect`、`PUT /api/settings`、`POST /api/open` |
| 表情 | 表情包库：网格浏览、标签筛选、搜索、点开改标签/删除、重建索引、迁移目录、采集设置 | `GET /api/stickers`、`GET /api/stickers/file`、`POST /api/stickers/{rebuild,tag,delete,migrate}`、`PUT /api/settings`、`POST /api/open` |
| 人格 | 人格库：多套人格新建 / 编辑 / 删除 / 一键切换，每个群可单独指定；下面是当前那套的正文编辑器 | `/api/personas`、`/api/personas/active`、`/api/personas/chat`、`/api/personas/seed`、`/api/persona` |
| 会话 | 每个 QQ 会话绑定的 DSH session，可删（删了下次重开） | `/api/sessions`、`DELETE /api/sessions/<id>` |
| 模型 | 跟随 DSH 桌面端 / 手动指定，含供应商与思考强度 | `/api/model` |
| 插件 | 插件开关、schema 自动生成的配置表单、加载失败清单 | `/api/plugins`、`PUT /api/plugins/<name>` |
| 系统 | 运行信息、开机自启、行为设置（唤醒词/匹配模式、限流、群成员权限、**黑白名单**、**群策略**）、日志 | `/api/settings`、`/api/logs`、`/api/autostart` |

### 2.3 前端约定

- 纯静态、无构建：`index.html` 里每个页签是一个 `section.page[data-page]`，底部 `nav-bar` 里一个 `button.nav-item[data-page]`。
- `app.js` 的 `PAGES` 表决定标题/副标题，`refreshPage(name)` 决定进页面时拉哪个接口。
- 视觉是 Material 3（令牌 `--md-sys-color-*` 映射成 `--primary`/`--surface-*` 等），深色模式跟随系统。
- 网站图标（favicon / apple-touch-icon）是 `src\webui\public\app-icon.png`（256×256），托盘与设置窗口复用 `assets\app-icon.png`，开机自启快捷方式用 `assets\app-icon.ico`。换图标只需替换这几张图（favicon 那张要单独缩到 256，别直接把 648 的丢进去）。

## 三、加功能的三种位置

按「改动的侵入程度」从轻到重：

### 3.1 只是多一个只读视图 → 加接口 + 加卡片

1. `src/webui/server.mjs` 里加一个 `GET /api/xxx`（读文件/读进程即可）；
2. `index.html` 对应页签里加 `<section class="card">`；
3. `app.js` 的 `PAGES`/`refreshPage`/渲染函数里接上。

不改桥接、不改启动流程，风险最低。

### 3.2 要改「收到消息之后、回复之前」的行为 → 写插件（推荐）

这是本次新增的能力，也是 AstrBot 插件模型的精简版。**加功能不用再动 `src/index.js`。**

#### 3.2.1 目录与最小插件

```
src/plugins/
  ping.js          ← 一个文件就是一个插件
  _*.js            ← 下划线开头会被忽略（放草稿/私有实验）
```

```js
// src/plugins/hello.js
export const meta = {
  name: 'hello',                 // 必须与文件名一致，只用 a-z0-9-
  displayName: '打招呼',
  version: '1.0.0',
  description: '被叫名字时先回一句问候（控制台里显示这段）',
  defaultEnabled: true,
  configSchema: [
    { key: 'greeting', type: 'string', label: '问候语', default: '在的' },
  ],
};

export async function onMessage(ctx) {
  if (!ctx.text.includes('在吗')) return undefined;
  await ctx.reply(`${ctx.config.greeting}～`);
  return { handled: true };        // 已经回过了，别再走 dsh
}
```

#### 3.2.2 三个钩子

| 钩子 | 时机 | 能做什么 | 返回值 |
| --- | --- | --- | --- |
| `onMessage` | 消息通过白名单/唤醒词判定之后，**调用 dsh 之前** | 指令类插件（`/ping`、`/help`）、消息预处理、直接回复 | `{handled:true}` 接管本轮；`{text:'...'}` 改文本；`undefined` 不表态 |
| `beforeReply` | 同上（`onMessage` 之后、组装 prompt 之前） | 改写要交给 dsh 的话术（翻译、脱敏、补上下文） | 同上 |
| `afterReply` | dsh 回完、**发到 QQ 之前** | 加签名、改格式、过滤敏感词 | `{text:'...'}` |

执行顺序：插件按文件名排序，**上一个插件的输出是下一个插件的输入**；任何插件抛错只记日志并跳过它，不影响其它插件，也不会影响回复。

#### 3.2.3 `ctx` 里有什么

```ts
{
  text: string;            // 当前文本（已过 sanitizeText、已去掉唤醒词）
  userId: number;
  nickname: string;
  isGroup: boolean;
  groupId: number | null;
  isOwner: boolean;        // 是否在 allowFrom 里
  message: object;         // 原始 OneBot 消息（只读）
  reply: (text: string) => Promise<void>;   // 想说什么直接调它
  log: Logger;
  config: Record<string, unknown>;          // 按 configSchema 合并好的配置
  meta: object;                             // 插件自己的元数据
}
```

#### 3.2.4 配置与开关存在哪

| 东西 | 位置 | 谁改 |
| --- | --- | --- |
| 开关 | `state/plugins.json` → `{ "ping": { "enabled": true } }` | 控制台「插件」页的开关 |
| 配置 | `config.json` → `plugins.ping.{...}` | 控制台「插件」页 schema 生成表单 |
| 目录 | `config.json` → `plugins.dir`（默认 `src/plugins`） | 手改配置 |

**生效方式：改完重启桥接**（控制台概览页或托盘菜单都能重启）。控制台会明说「重启后生效」，不会假装已经热加载。

#### 3.2.5 schema 支持的字段类型

`string`（单行）、`text`（多行 textarea）、`bool`（开关）、`int`（数字）、`select`（下拉，需给 `options`）。
控制台会按类型渲染控件，写盘时统一 `coerceValue` 收敛，插件拿到的配置一定是对的型别。

### 3.3 要改「进程本身」→ 托盘菜单或启动脚本

比如新增一个要常驻的子进程、要开机自启的东西：改 `launcher/Launcher.ps1` 的菜单与 `lib/ProcessControl.ps1` 的启停函数，再在 `src/webui/server.mjs` 的 `SERVICE_NAMES` 里登记，控制台就能跟着启停。

## 四、和桥接主流程的关系

```
OneBot 消息
  → 白名单 / 群号 / @ 或唤醒词            (src/security.js)
  → 群记忆先记一条（不管回不回）          (src/groupmem.js)
  → 插件 onMessage / beforeReply          (src/plugins.js)  ← 可以在这里结束
  → 限流
  → 记忆检索（Obsidian）                  (src/memory.js)
  → 串行队列 → 调 dsh                     (src/dsh.js + src/model-follow.js)
  → 插件 afterReply                       (src/plugins.js)
  → 分片发送 → 写长期记忆
```

插件被放在「决定要不要回」之后，是因为它**不该重做白名单判断**；被放在限流之前，是因为指令类插件很便宜，不该被聊天限流挡住。这些顺序在 `src/index.js` 里有注释，改动前先读。

## 五、已知限制与路线图

| 限制 | 影响 | 计划 |
| --- | --- | --- |
| 插件生效要重启桥接 | 改完不能立刻用 | 后续可加一个 `SIGUSR`-风格的重载信号或本机控制口 |
| 插件不能自己 inject 前端页面 | 复杂插件只能通过「配置 + 系统页」露脸 | 需要时再引入静态资源目录白名单 |
| 控制台无鉴权 | 只绑 127.0.0.1，本机其他程序能访问 | 与「公开源码」冲突时再评估，公开版默认只读演示数据 |
| 控制台与桥接只靠磁盘同步 | 状态有最多 5 秒延迟（`status.json` 每 5 秒写一次） | 够用，不改 |

## 六、验证

```powershell
node tests\plugins-test.mjs      # 插件宿主单测（39 项）
node tests\e2e-plugins.mjs       # 真桥接 + 假 dsh：接管不调 dsh、afterReply 生效（7 项）
node tests\run-all.mjs --only 插件
```

插件链路的证据点：`status.json` 的 `plugins` / `pluginsFailed` 字段、桥接日志里的「插件已加载 N 个」「插件接管了这条消息」，以及控制台「插件」页的失败清单。
